# 参考分析：下厨房+

## 参考定位

“下厨房+”可以作为菜谱类小程序的体验参考，但它的核心定位更接近公开菜谱内容平台，而本项目第一版定位是私人、本地、轻量的菜谱本。

参考时应提炼体验结构，不直接照搬功能规模。

## 公开资料中的能力特征

根据公开介绍，“下厨房+”主要围绕这些能力展开：

- 浏览和搜索美食菜谱
- 查看菜谱详情和制作步骤
- 图文教学，部分内容包含视频教程
- 收藏和分享菜谱
- 食材搭配、家常菜、快手菜等内容分类
- 基于大量用户分享内容形成菜谱库

## 可借鉴的体验

### 1. 搜索是高频入口

菜谱类产品里，用户经常带着明确目标进入，例如“番茄炒蛋”“汤圆”“快手菜”。

本项目第一版应保留首页搜索，并让搜索框足够明显。搜索范围先只覆盖用户本地保存的菜名，后续可以扩展到食材、做法和备注。

### 2. 图片是判断入口

菜谱列表不能只靠文字。图片能帮助用户更快回忆“这是不是我想找的那道菜”。

本项目首页卡片应优先展示图片；没有图片时使用稳定的占位状态，避免列表显得破碎。

### 3. 详情页要适合边做边看

公开菜谱平台通常强调步骤清晰，因为用户会在厨房场景中查看。

本项目详情页虽然不做复杂教程，也应让“食材”和“做法”清楚分区，文字字号和行距适合手机上快速扫读。

### 4. 分类要贴近做饭语境

“家常菜”“快手菜”“下饭菜”等分类比抽象分类更有行动感。

本项目第一版已有固定分类，后续可以考虑加入更生活化的标签，例如：

- 快手
- 下饭
- 适合带饭
- 适合早餐
- 家人爱吃

### 5. 收藏逻辑可转化为“常做”

公开平台里的收藏是把别人的菜谱留起来。本项目是私人菜谱本，不需要收藏别人的内容。

可以把这个心智转化为“常做”或“喜欢”，用于后续排序和“今天吃什么”随机选择。

## 不建议第一版照搬的功能

- 公开菜谱库
- 用户发布和关注
- 评论、点赞、社区互动
- 视频教程
- 食材购买或电商转化
- 复杂推荐算法
- AI 识图生成菜谱

这些能力会显著增加内容、审核、账号、服务端和运营成本，不适合第一版本地原型。

## 对本项目的调整建议

第一版保持现有 MVP，但可以吸收以下细节：

- 首页搜索框放在明显位置。
- 菜谱卡片优先展示图片、菜名、分类、更新时间。
- 详情页把“食材”和“做法”分成两个清楚区域。
- 编辑页仍然轻量，不强迫填写完整步骤。
- 在数据模型中预留 `tags` 或后续标签扩展空间，但第一版可以不实现。
- 后续版本加入“常做”标记，用于排序和随机推荐。

## 核心差异

| 方向 | 下厨房+ | 本项目 |
| --- | --- | --- |
| 产品定位 | 公开菜谱分享平台 | 私人本地菜谱本 |
| 内容来源 | 平台和用户分享 | 用户自己记录 |
| 主要行为 | 找菜谱、学做法、收藏分享 | 记录、浏览、再次找到 |
| 是否需要账号 | 平台型能力通常需要账号支撑 | 第一版不需要 |
| 是否需要服务端 | 需要内容和用户体系 | 第一版不需要 |
| 第一版重点 | 内容消费 | 本地记录闭环 |

结论：下厨房+适合作为“菜谱浏览体验”的参考，不适合作为第一版功能范围的模板。我们的第一版应继续小而稳，先验证用户是否愿意持续记录自己的菜。
