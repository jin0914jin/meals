# 本地数据设计

## 数据策略

第一版采用本地优先，不接服务器。

推荐做法：

- 文本数据保存在小程序本地存储中
- 图片通过小程序文件能力保存到应用沙盒
- 列表页读取本地菜谱集合

## 菜谱数据模型

每一道菜建议包含：

| 字段 | 说明 | 是否必填 |
| --- | --- | --- |
| id | 本地唯一标识 | 是 |
| title | 菜名 | 是 |
| category | 分类 | 否 |
| ingredients | 食材 | 否 |
| steps | 做法 | 否 |
| note | 备注 | 否 |
| imagePath | 本地图片路径 | 否 |
| createdAt | 创建时间 | 是 |
| updatedAt | 更新时间 | 是 |

## 分类数据

第一版可以先使用固定分类：

- meat：荤菜
- vegetable：素菜
- soup：汤
- staple：主食
- breakfast：早餐
- dessert：甜品
- quick：快手菜
- other：其他

如果第二版要支持自定义分类，可以再新增分类表。

## 本地存储键建议

为了后续维护清楚，建议统一命名：

| 键 | 用途 |
| --- | --- |
| recipes | 菜谱列表 |
| appSettings | 本地设置 |
| schemaVersion | 本地数据版本 |

## 图片处理原则

第一版不要做复杂图片编辑。

建议只做：

- 拍照
- 从相册选择
- 保存到小程序本地沙盒
- 详情页和列表页读取显示

暂不做：

- 裁剪
- 滤镜
- 压缩参数配置
- 多图

## 数据迁移预留

即使第一版很简单，也建议保留 `schemaVersion`。这样后面从本地单机版升级到云同步、家庭共享或多端同步时，不需要推倒重来。

## 风险点

### 小程序本地存储容量有限

如果用户保存大量图片，本地空间可能不够。第一版可以接受这个限制，但后续需要考虑云存储或图片压缩。

### 临时图片路径不可长期依赖

拍照或选图得到的临时路径应保存为小程序本地文件路径，再记录到菜谱数据里。

### 用户换手机会丢数据

第一版不做账号和云同步，所以需要在产品说明里接受这个限制。第二版可以加入导出/导入或云端备份。
